# meeting-scribe

Пользователь даёт путь к аудио встречи. Агент делает транскрипт и фоллоу-ап; интерфейса нет. Эти инструкции общие для Codex и Claude Code (`CLAUDE.md` ссылается сюда).

## Среда и рабочая папка

- Команды выполнять из корня проекта. Зависимости Python ставит `uv`; нужны ffmpeg и ffprobe. Ключ `OPENROUTER_API_KEY` — в `.env` или окружении.
- Обрабатывать встречи в основной локальной папке проекта, где уже лежат `meetings/`, `.env` и `glossary.txt`. Они игнорируются Git и автоматически не переносятся в worktree. Без старого `meetings/` нет кэша, и запись может распознаться повторно за деньги. Worktrees использовать для правок кода и синтетических тестов; настоящие записи там не запускать.
- Долгий запуск оставлять в управляемой сессии инструмента и дождаться завершения; не завершать работу на сообщении «запущено». Стоимость брать из вывода скрипта: всего и за этот прогон.
- Для вопросов использовать доступный инструмент с вариантами ответа; если его нет — вопрос с вариантами обычным сообщением. Не угадывать ответы, которые знает только пользователь.
- В ответах Codex давать абсолютные ссылки на файлы. Аудиофрагмент показывать плеером: `![Фрагмент](/абсолютный/путь/к/фрагменту.mp3)`.
- [Шаблон фоллоу-апа](docs/followup-template.md) прочитать перед его составлением. [Устройство движков и наблюдения](docs/recognition-notes.md) — при изменении распознавания или разборе ошибок; детали экспериментов не нужны для каждой встречи.

## Процесс

1. Запустить `uv run scribe.py "<аудио>" [--name <slug>] [--terms "Имя Фамилия,Термин"]`.
   - Если тема известна, сразу задать slug через `--name`. Результат — `meetings/<дата>-<slug>/`: `transcript.md`, `transcript.json`, ответы API в `raw/`.
   - Постоянные имена и термины — в необязательном `glossary.txt`, по строке. MAI получает первые 50 подсказок из `--terms` и словаря, Scribe подсказок не получает. MAI может вставлять подсказанные слова туда, где их не говорили: проверять имена на шаге 2.
   - Дата папки — из `creation_time`, иначе даты создания файла (на Linux — изменения); это не обязательно дата встречи.
   - Повторный запуск ищет запись после переименования папки и использует кэш. Новые `--terms` на кэш не действуют. Удаление `raw/words_*.json` вызывает платное перераспознавание слов; не делать этого при проверке кода.
   - Если есть WARNING об упавшем MAI, один раз повторить ту же команду: платится только отсутствующий кусок. Если упал Scribe, перезапуск тоже использует удачные куски. При 401/402 сообщить о ключе/балансе и остановиться.
   - Первый Ctrl-C дожидается уже оплаченных запросов и сохраняет ответы в `raw/`; второй их бросает.
   - Zoom может уже назвать спикеров: в выводе `Zoom and the microphone named N% of words; own voice: ...`. Если записывающий остался «Спикер N», спросить имя. `Zoom lit only <имя> all call long` — застрявшая подсветка: имён из Zoom нет, назвать по контексту.
2. Прочитать `transcript.md` целиком, длинный — последовательными частями до конца. Определить тему и имена по обращениям, представлениям и ролям. Неуверенное имя оставить «Спикер N»; ники Zoom вроде «iPhone» заменить, только если настоящее имя ясно.
   - Переименовать папку по теме, сохранив дату: `mv meetings/<дата>-<старый> meetings/<дата>-<slug>`. Последующие запуски — без `--name` или с новым slug.
   - Применить имена: `uv run scribe.py names meetings/<dir> 1=Андрей 2="Мария (дизайн)"`. `N=` снимает имя; одно имя у нескольких меток допустимо.
   - Пересказ незаписанного начала со слов пользователя сохранить почти его словами в `note.md` папки записи: он добавляется при каждой сборке. `transcript.md` вручную не править — это производный файл.
   - Несколько записей одной встречи: обработать каждую, затем `uv run scribe.py join meetings/<dir-1> meetings/<dir-2>`. Вторая переезжает вместе с кэшем в `<dir-1>/2/`; общий транскрипт — в первой папке, таймкоды `[1·ЧЧ:ММ:СС]` и `[2·ЧЧ:ММ:СС]`, безымянные — «Спикер N·M». Имена и `note.md` второй менять в `2/`. Перезапуск найдёт её там; `--name` для неё игнорируется.
   - Имена и термины из подсказок сверять со словами Scribe: `raw/speakers_<начало>-<конец>.json`, поле `words` (`word`, `start`, `speaker_label`); `start` — от начала куска. Оба движка ошибаются в именах. Если расходятся, дать пользователю аудиофрагмент и вопрос с вариантами; не выбирать самостоятельно.
   - Для фрагмента создать `clips/` и выполнить `ffmpeg -v error -ss <с> -to <с> -i "<запись>" -ac 1 -c:a libmp3lame -q:a 4 "meetings/<dir>/clips/<N> — <ЧЧ-ММ-СС> <о чём>.mp3"`. Секунды — `start` и `end` реплики в `transcript.json`.
   - На очных встречах одна метка может объединять нескольких людей. Имя определять по содержанию реплики; неясные метки показать пользователю двумя-тремя характерными цитатами с вариантами ответа.
   - Правки по просьбе пользователя вносить в `transcript.json`, `utterances`: `text` и `speaker` (номер метки; новый номер можно назвать через `names`). Смешанную реплику разрезать. Команда `names` пересоберёт Markdown. **Повторный запуск распознавания, даже из кэша, стирает ручные правки реплик.**
   - Если пользователь просит полную выверку, сверить MAI со Scribe кусками примерно по 30 минут: один субагент на кусок предлагает правки по номерам реплик, главный агент сверяет каждую. Слова Scribe брать из соответствующего куска без 5-минутного нахлёста. По словам по умолчанию верить MAI; без опоры на Scribe или явный контекст правку не вносить.
3. Написать `followup.md` по [шаблону](docs/followup-template.md).
   - Кто что сказал, определять по содержанию, а не только меткам спикеров.
   - Решение — то, на чём сошлись. Задача — то, что человек взял на себя, включая явное согласие на поручение. Неясное принятие — открытый вопрос. Совет или предложение без согласия — ход обсуждения, а если ждёт ответа — открытый вопрос.
   - Дата — со слов пользователя, иначе из метаданных в начале транскрипта, речи или имени файла. `creation_time` может оказаться временем выгрузки: сверять с речью. Если даты нет — дата папки с «(?)». Сроки и ответственных не придумывать.
   - Ссылки на транскрипты — отдельными строками: `share` удаляет эти строки целиком. Пояснение таймкодов писать без ссылок.
4. Проверить фоллоу-ап **одним независимым субагентом на встречу** через доступный инструмент запуска субагентов. Он читает транскрипт целиком, файлы не меняет; ищет ложные утверждения, предложения, выданные за решения/задачи, неверные цифры, нарушения шаблона и пропущенные договорённости. Каждое замечание — с таймкодом и цитатой. Главный агент сверяет замечания и исправляет файл. Если инструмент недоступен, явно сообщить, что независимая проверка не выполнена.
5. Ответить коротко: ссылки на файлы и суть в 3–5 строк; упомянуть плохие куски записи. Через вопрос с вариантами уточнить неопознанных спикеров, отсутствующую дату, неясные суммы/ответственных и адресатов: участники или только свои. Для участников убрать оценки людей, сказанное после ухода человека и цифры «без распространения»; пока адресаты не уточнены, готовить версию для участников. По ответам поправить файлы.
6. Сделать копию для Telegram: `uv run scribe.py share meetings/<dir>` → `Итоги встречи ДД.ММ — <тема>.md` без ссылок на транскрипт. Длинную тему сократить вторым аргументом: `share meetings/<dir> "Урал Пресс, заявки"`. После правок повторить `share`: старые копии удаляются. PDF — только по просьбе.

## Изменения кода и проверки

- После правок `scribe.py`: `uv run test_scribe.py`. Синтетический звук генерирует ffmpeg, HTTP-запросы подменены; реальные запросы в тестах запрещены.
- Старые встречи проверять командой `uv run scribe.py check meetings/<dir>`. Она пересобирает временную копию, включая объединённые записи, строго из кэша, без ключа API и без изменений оригинала. Код выхода 0 — результат совпал, 1 — различия или ошибка. Различия могут быть ручными исправлениями: изучить причину, не затирать их автоматически.
- `uv run scribe.py "<аудио>" --cache-only` запрещает API-запросы и прекращает работу при отсутствии любого куска, в том числе после изменения нарезки. Это **пересборка**, она меняет исходный транскрипт; для проверки использовать `check`.
- При проверке изменений не тратить деньги, не удалять кэш, не перезапускать обычное распознавание старых встреч. Не менять `CHUNK`, `plan`, `quietest`, модели или Zoom-разметку без учёта [заметок](docs/recognition-notes.md): это влияет на кэш и имена. Если меняется `by_zoom`, проверить ручные имена там, где изменились говорящие.
